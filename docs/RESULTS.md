# Measured results

Every number here names the command that produced it and the machine it ran on. Numbers that
require Intel Core Ultra hardware are marked as pending rather than substituted with a
development-machine figure.

**Development machine** (all non-Intel numbers below): AMD Ryzen 7 250, 16 threads, 15 GiB RAM
under WSL2, NVIDIA RTX 5050 Laptop (8 GB), MuJoCo 3.13.0 rendering on the CPU (no GPU OpenGL
under WSL).

## 1. Perception

```bash
python scripts/eval_perception.py --seeds 10 --json outputs/perception.json
```

| Metric | Value |
| --- | --- |
| Recall (visible objects detected) | **0.92** |
| Precision (detections that are real objects) | **0.84** |
| Mean position error | **8.6 mm** |
| p95 position error | 35.5 mm |
| Category accuracy | 0.79 |
| Colour accuracy | 0.93 |

Measured against simulator ground truth, which is used *only* for scoring. Objects shut inside the
drawer are excluded from recall — not seeing through wood is correct behaviour.

The 8.6 mm mean error is why grasps of thin features (a plate rim is 9 mm) use wrist-camera
refinement at the pre-grasp hover rather than relying on the overhead estimate alone.

## 2. Workspace and hardware limits

Generated by `python scripts/measure_workspace.py` into [WORKSPACE.md](WORKSPACE.md).

| Fact | Value | Consequence |
| --- | --- | --- |
| Reach at table height | 0.14–0.34 m | Table sized to match; objects never spawn outside it |
| Shoulder actuator limit | 2.94 N·m | Poses that sag are rejected by the IK, not attempted |
| Jaw aperture | 4–133 mm | Sets which grasps are possible at all |
| Tool site vs jaw line | ~20 mm offset | Grasps are specified as where the *object* sits, not the tool |
| Render cost (224×224, shadows on / off) | 285 ms / 96 ms | Collection disables shadows and runs 6–10 workers |

## 3. Benchmark suite (analytical controller)

```bash
python scripts/evaluate.py --seeds 10 --workers 6 --out outputs/eval_baseline
```

Reported per tier: task success (all criteria), criterion score (fraction of criteria met),
subtask success (fraction of executed steps that worked), and the failure attribution histogram.

The suite is 11 tasks × 10 seeds = 110 episodes. Episodes are a pure function of `(task, seed)`,
so `--workers` shards them across processes without changing any result — which is what keeps the
headline number cheap enough to re-measure after a change.

**Measured over all 110 episodes** (analytical controller, camera perception, full randomization
per tier):

| Tier | Episodes | Task success | Criterion score | Subtask success |
| --- | --- | --- | --- | --- |
| 1 — placement | 20 | 0.75 | 0.75 | 0.59 |
| 2 — disambiguation | 20 | 0.85 | 0.85 | 0.66 |
| 3 — drawer dependency | 10 | 0.00 | 0.40 | 0.10 |
| 4 — pour + hand-off | 20 | 0.30 | 0.30 | 0.17 |
| 5 — full randomization | 20 | 0.25 | 0.47 | 0.41 |
| 6 — hero / style | 20 | 0.25 | 0.41 | 0.39 |
| **all** | **110** | **0.436** | **0.543** | **0.412** |

Failure attribution: reachability 53, grasp 39, manipulation 15, placement 10.

Reachability dominates, which is the honest consequence of a 0.14–0.34 m workspace: the IK
*refuses* poses whose shoulder torque exceeds 2.94 N·m rather than attempting them and sagging.
Tier 3 scores zero at task level while scoring 0.40 on criteria, and the split is informative:
the drawer is opened successfully in **all ten seeds** (90–110 mm), and the utensil inside it is
then never moved to the setting — every one of those failures is attributed to `reachability`.
The dependency itself works; what the arms cannot do is reach into the opened drawer and place
what is in it.

## 4. Demonstration dataset

```bash
python scripts/collect_dataset.py --episodes-per-skill 60 --workers 6
```

| | |
| --- | --- |
| Format | LeRobotDataset v3.0, video-encoded |
| Cameras | 3 × 224×224 (overhead, left wrist, right wrist) |
| State / action | 12-dim each (5 joints + gripper, per arm) |
| Label | the instruction sentence that produced the episode |
| Episodes / frames | 307 / 57,844 |
| Expert success rate | ~58% — only successful episodes are kept (193 kept from 330 attempts on the placement pass) |
| Collection rate | 5.5 episodes/min with 6 workers |

Randomization during collection: placement, object size, mass. Lighting, friction, colour and
clutter are held fixed because they drop the expert's success rate to ~25%, which would shrink the
dataset threefold. Evaluation uses the full randomization.

## 5. Policy training

```bash
python scripts/train_policy.py --policy smolvla --steps 20000
```

| | |
| --- | --- |
| Model | SmolVLA (`lerobot/smolvla_base`), 450 M parameters |
| Trainable | action expert only; SigLIP vision tower frozen |
| Batch | 2 × 16 gradient accumulation = effective 32 |
| Images | 256×256 (dataset is 224×224; padding to the pretrained 512 adds no information and costs ~4× the vision compute) |
| Measured step time | 0.22 s/step at batch 2; **0.46 s/step at batch 16** (2.17 steps/s) → 20k steps ≈ 2h26m |
| Bottleneck | GPU compute at batch 16 (`updt_s` 0.44, `data_s` 0.007). At batch 2 it was the dataloader instead, which is why the larger batch is nearly free |

Two integration details that are easy to miss and cost an hour each: SmolVLA's pretrained config
names its cameras `camera1..3`, so a `--rename_map` is required; and torchcodec needs real FFmpeg
shared libraries, which this repo installs into `.venv/ffmpeg` via conda.

## 6. Policy versus analytical controller

```bash
python scripts/evaluate.py --policy <checkpoint> --seeds 10 --out outputs/eval_policy
python scripts/evaluate.py --policy <checkpoint> --no-fallback --seeds 10   # policy alone
```

The deployed system is **pure VLA**: every joint command comes from the policy and nothing rescues
a failed subgoal. Two columns are reported on the same tasks and seeds — the analytical baseline
(what the demonstration generator achieves) and the policy — so the gap between them is visible
rather than papered over.

### Policy-only progress, and what actually limits it

```bash
python scripts/evaluate.py --tier 1 --seeds 4 --workers 1 --policy <ckpt>
```

Training on 307 demonstrations (of which ~280 are placement) reaches a training loss of 0.021 by
12k steps and stops improving. Task success does not follow the loss, so the interesting
measurement is not the loss curve but **where the policy is asked to act**:

| Scenes | Seeds | Episodes | Task success |
| --- | --- | --- | --- |
| **Held out** (never collected) | 0–3 | 8 | **0/8** |
| **Trained on** (in the dataset) | 8001, 8005, 8021, 8023 | 4 | **2/4** |

Both columns use the identical scene generator, the identical instruction and the identical
success criterion — only the seed differs. If the true success rate were the 50% seen on trained
scenes, drawing 0/8 on held-out scenes has probability ~0.4%, so the gap is real and not sampling
noise.

That single comparison rules out most of the things that usually explain a policy that "does
something plausible but never succeeds", and each was checked directly:

* **Not a wiring bug.** The camera rename map (`top→camera1`, `left_wrist→camera2`,
  `right_wrist→camera3`) is saved inside the checkpoint's processor pipeline and applied at
  inference, and the action layout is symmetric between collection and the runner
  (`actuator_ids[:5] == arm_actuators`, `actuator_ids[5] == gripper_actuator`).
* **Not a dead policy.** Over a 20 s episode the left arm's joints travel 3–8 rad with a
  commanded-action standard deviation of 0.19–0.25, while the right arm holds station
  (std 0.007–0.012) — which is the correct division of labour for a one-armed placement.
* **Not a distribution mismatch in the scene generator.** Tier 1 and the collection pass both use
  `RandomizationConfig.placement_only()`.

What is left is **generalization**: the policy has learned the skill on the scenes it saw and does
not transfer to new object placements. The lever for that is demonstration diversity, not more
gradient steps — which is why the second collection pass widens randomization to object size and
mass rather than simply training longer.

### Cost of one episode, and where it goes

SmolVLA predicts a 50-step action chunk. LeRobot's `select_action` hides that chunk in a queue
inside the policy and hands back one action at a time, which is efficient for the network and
wrong for the caller: the runner asked for an action every tick, so it rendered three camera
frames every tick to feed an inference that only happens every 50th. Under this project's CPU
renderer that is 150 frames rendered per inference.

`LeRobotBackend.predict_chunk` asks for the horizon directly, so observation cost tracks inference
cost. Measured on the same task, seed and checkpoint (tier 1, seed 0, 10k-step checkpoint):

| | Wall per episode | Sim per episode |
| --- | --- | --- |
| One action per call (`select_action`) | 377 s | 21.2 s |
| Whole chunk per call (`predict_chunk`) | **34.5 s** | 21.2 s |

**10.9× faster for identical behaviour.** The same seeds, the same policy, the same number of
network evaluations — only the wasted rendering is gone. This is what makes a 110-episode,
10-seed policy evaluation affordable at all.

### Inference latency (measured)

| Statistic | Value |
| --- | --- |
| One chunk inference, CUDA | **~450 ms** (50 actions → ~9 ms per executed action) |
| Vision tower, OpenVINO fp16 CPU | 60.3 ms per camera × 3 cameras |
| Vision tower, OpenVINO INT8 CPU | 35.2 ms per camera |

At 20 Hz control a 50-step chunk buys 2.5 s of motion per inference, so the network is not on the
critical path — but three camera encodes are, and that is precisely the workload an iGPU or NPU
exists to absorb.

## 7. Intel / OpenVINO

```bash
python -m armanual.cli devices
python scripts/benchmark_intel.py --checkpoint <ckpt> --export --precisions fp16 int8 \
    --devices CPU GPU NPU --out outputs/benchmarks/core_ultra.json
```

**The export and benchmark chain is proven end to end**, measured on the development machine
(AMD Ryzen 7 250, OpenVINO 2026.3.1, CPU plugin only — `is_intel_core_ultra: false`):

| Component | Precision | Size | Compile | Warm-up | p50 | Throughput |
| --- | --- | --- | --- | --- | --- | --- |
| SmolVLA vision tower (86.4 M params) | fp16 | 173.4 MB | 0.5 s | 170 ms | **60.3 ms** | 16.6 Hz |
| SmolVLA vision tower | INT8 (NNCF) | **87.9 MB** | 0.5 s | — | **35.2 ms** | 28.4 Hz |
| SmolVLA vision connector (11.8 M) | fp16 | 23.6 MB | — | — | **0.95 ms** | ~1050 Hz |
| SmolVLA action expert (98.2 M) | — | did not convert | — | — | — | — |

The action expert is a Llama stack and `torch.jit.trace` fails on it (`unordered_map::at`), with
`use_cache=False` and eager attention both tried. It stays on PyTorch, and that is reported rather
than worked around — see [INTEL.md](INTEL.md) for the full component table.

INT8 gives **1.97× smaller and 1.71× faster** on the same graph, calibrated on frames rendered
from the robot's own three cameras rather than a generic image corpus.

Why this matters for device placement: the vision tower runs **once per camera**, and the policy
uses three. At 60 ms each that is ~180 ms of vision per inference on a CPU — the single largest
term in the loop, and precisely the workload an iGPU or NPU exists to absorb.

*The Core Ultra figures are pending access to the target machine.* The harness runs anywhere and
stamps `is_intel_core_ultra` into every results file, so a development-machine measurement can
never be mistaken for a target-hardware one.

What will be reported: per component (vision tower, action expert) × per device (CPU/iGPU/NPU) ×
per precision (fp32/fp16/INT8): compile time, warm-up latency, steady-state p50/p95/max,
throughput, model size — plus task success on the same seeds before and after optimization.
